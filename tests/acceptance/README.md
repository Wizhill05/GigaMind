# Local adoption and recovery acceptance

Run from the repository root with `/tmp/gigamind-audit-venv/bin/python -m pytest -q tests/acceptance/test_adoption_recovery.py`. This test always owns its loopback server and pytest temporary SQLite files; it has no option to target an existing server. The subprocess receives a small environment allowlist, disables dotenv, and uses a synthetic master key. It starts no worker and configures no external provider or storage credentials. Server readiness, shutdown, SDK operations, and backup commands have deadlines. The owned temporary directory is removed after the test, including on failure.

Two distinct scoped MCP SDK identities exercise proposal evidence, administrative approval, supersession, handoff, issue reporting, project isolation, rotation and revocation. HTTP checks cover queued job state and review history. The server is restarted on the original database, then the shipped backup and restore CLI creates a new destination with a verified snapshot digest; the checks are repeated against a fresh server on that destination. Captured server output is checked for synthetic tokens and knowledge content. The test does not prove every possible log message is safe.

The queued index job is deliberately never processed. No actual file storage, provider ingestion, embeddings, semantic retrieval, cloud service, or external identity provider is exercised. MCP SDK identities are not verified vendor AI hosts. Host-specific adoption and live provider/storage acceptance remain necessary; this scenario does not establish production readiness.
